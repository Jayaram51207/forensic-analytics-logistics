# Cross-Application Evidence Provenance and Contradiction-Guided Incident Reconstruction

Implementation: `forensics/src/provenance.js`, integrated through `analyze()` and `caseDetail()` in `forensics/src/cases.js`, shown in the dashboard (`forensics/public/index.html`) and returned by `GET /api/cases/:id`.

## 1. The problem this addresses

The first version of the framework detected inconsistencies **inside** one job record. It could not answer three questions an investigator asks next:

1. *Where did this value come from?* Was it read from a document, or typed?
2. *Do the records that agree actually corroborate each other?* Five documents repeating one typed number are one statement, not five.
3. *Does another application say something different?* The same shipment is described in the synchroniser, in B.I.I.L. documents, in a packing run and in a stuffing report, with no shared key.

## 2. Four properties kept apart

| Property | Question | What this system can say |
|---|---|---|
| Integrity | Is the captured record unchanged since capture? | Yes or no, from the hash chain and (if configured) the external anchor |
| Authenticity | Did the original source really say this? | **Never established.** Uploaded files are hashed, not authenticated |
| Accuracy | Is the value true? | **Never established.** Agreement is reported as corroboration strength only |
| Independence | How many separately sourced records agree? | Counted from lineage |

Every case carries a `trust` block stating each of the four. A verified hash chain around a false number is still a false number, and the dashboard says so.

## 3. Evidence items

`buildProvenance(view, context, config, integrity)` produces `items[]`. Each item has:

| Field | Meaning |
|---|---|
| `evidence_id` | Stable id (`EV-…`) derived from kind, event, field and parents |
| `kind` | `source_document`, `extracted_value`, `recorded_value`, `generated_artifact`, `external_record` |
| `derived` | `false` for source evidence; `true` for anything computed or copied from another item |
| `application`, `event_id`, `source_record_id` | Where it was captured; for outbox records, the tool's own record id |
| `field`, `original`, `normalized`, `unit` | The value as written, and as parsed. The original is never replaced |
| `event_time`, `time_basis`, `ingested_at` | When it happened by its own clock; which clock; when it reached the store |
| `actor` | Name, source and whether verified |
| `transformation` | What produced it: regex extraction, template fill, autofill/re-typing, or "no source reference captured" |
| `parents` | Evidence ids it derives from |
| `root` | Lineage root (see §4) |
| `artifact` | Path, SHA-256, content fingerprint for files |
| `record_integrity` | Verified in chain / failed / not checked in this run |
| `entity_match` | How the record was tied to this shipment, and with what confidence |
| `unverified`, `not_comparable`, `assumption`, `lineage_note` | What is not known about it |

Rule findings, normalised values, parsed values and generated documents are different kinds. None is substituted for another.

## 4. Lineage roots

| Root | Assigned to | Meaning |
|---|---|---|
| `doc:<sha256>` | An uploaded source document; values extracted from it; a job value equal to the extracted value at creation; a B.I.I.L. record that lists the same file hash among its sources | One document |
| `entry:<event>:<field>` | A job value that does not match any extracted value, and every later edit | Typed by someone at that event; where they took it from was not captured |
| `derived:workflow_sync_job` | Workbooks generated by the synchroniser | Copies of the job record; never a separate witness |
| `app:<application>` | Records from a desktop tool with no shared source file | Recorded separately in that tool. All records from one tool for one shipment share this root, however many times they are exported |

**What is not known is stated, not filled in:**
- The synchroniser does not record where a typed value came from.
- B.I.I.L. does not record whether a field was parsed or typed, so its lineage is marked unknown even when it shares a source file.
- The PDF parser does not report where in the file a value was found.
- Generated workbooks are not read back; their content is inferred from the generator's input.

## 5. Corroboration

For each comparable field of the job (`gross_weight`, `net_weight`, `packages`, `invoice_no`, `shipping_bill_no`, `container_nos`, `taxable_total`, `job_no`):

- `agreeing_records`: records holding the same value (within tolerance).
- `independent_roots`: distinct roots among them.
- `copies_of_same_source`: `agreeing_records − independent_roots`.
- `weak_agreement`: matches that rest on an assumption (packing manifests). Not counted as roots.
- `needs_independent_source`: true whenever there is one root.
- `statement`: a sentence for the reviewer.

Records that cannot be attributed (ambiguous link, or confidence below `min_link_confidence`) are excluded.

"Separately sourced" here means separately recorded inside one organisation. That is weaker than an outside authority, and the statement says so.

## 6. Contradiction rules

A contradiction compares the job's **current** value with a linked record from another application. All rules are version 1.0.

| Rule | Compares | Notes |
|---|---|---|
| `XAP-GROSS_WEIGHT`, `XAP-NET_WEIGHT` | Job weights vs B.I.I.L. fields, stuffing-report row, packing manifest total | Manifest comparison is assumption-based |
| `XAP-PACKAGES` | Job package count vs B.I.I.L., stuffing report, manifest quantity | Manifest comparison is assumption-based |
| `XAP-INVOICE_NO`, `XAP-SHIPPING_BILL_NO` | Number part of the combined number+date strings | |
| `XAP-CONTAINER_NOS` | Set of container numbers | |
| `XAP-TAXABLE_TOTAL` | Sum of job charges vs sum of B.I.I.L. charges | Before tax, so no tax rule is involved |
| `XAP-TAX` | Same taxable total, different grand total | Always `unresolved_business_rule_conflict` |
| `XAP-JOB_NO` | A record linked through something other than the job number names a different job | |
| `XAP-TIMING` | A desktop-tool record made after the job was closed or deleted | Order is not asserted when clocks differ and times are close |
| `XAP-UNATTRIBUTED` | A record that differs but cannot be attributed to one job | One note per record, always `insufficient_evidence` |

Not implemented, because the fields do not support it: quoted charges (EasyQuote) against invoiced charges. EasyQuote amounts are free text ("Rs.9500/- per 20ft", "AT ACTUALS") and the tool has no shipment reference. Its exports are captured and stored; nothing compares them.

Each contradiction keeps: both evidence items with original and normalised values, event ids, times and clocks; the difference; `independence` (`shared_ancestor`, `separately_recorded`, `independent_source_document`); `entity_match`; `ordering` with an `uncertain` flag; `missing_business_rule`; `supported_by[]`; `weakened_by[]`; an explanation and a recommended next step.

### Classification

| Classification | When | Scored as |
|---|---|---|
| `insufficient_evidence` | Link ambiguous or below `min_link_confidence`; or two close times from different clocks | note |
| `unresolved_business_rule_conflict` | The difference is explained by two tax implementations, neither authoritative | note |
| `suspected_operational_anomaly` | Comparison rests on an assumption (packing manifest); or activity after job end | anomaly, low |
| `confirmed_data_inconsistency` | Two attributable records state different values | anomaly, medium |
| `potential_fraud_indicator_requiring_investigation` | A numeric difference where (a) the uploaded source document agrees with the other record, or (b) the job itself held the other record's value until it was edited | anomaly, high |

"Confirmed" refers to the inconsistency: the two records demonstrably differ. Nothing is said about which is right or why. No classification asserts fraud.

### Configuration (`PROVENANCE_CONFIG`, override through `analyze(records, { provenance_config })`)

| Key | Default | Status |
|---|---|---|
| `min_link_confidence` | 0.5 | Chosen |
| `weight_tolerance`, `money_tolerance` | 1 kg / 0.5 %; 1 / 0.1 % | Chosen |
| `compare_packing_manifest` | true | **Assumption**: the manifest describes the whole consignment |
| `packing_weight_tolerance` | 50 kg / 5 % | Chosen |
| `clock_skew_minutes` | 10 | Chosen |
| `enabled_comparisons` | all | Remove a name to switch a comparison off |

Switches for ablation: `analyze(records, { provenance: false })`, `{ contradictions: false }`, `{ timeline_order: 'sequence' }`.

## 7. Contradiction-guided reconstruction

A case detail now contains, besides findings and timeline:

- `provenance.contradictions`, `provenance.corroboration`, `provenance.external_records`, `provenance.missing_independent_evidence`, `provenance.trust`, `provenance.items`.
- Per finding, `assessment.supports[]` and `assessment.weakens[]`: unverified actors, incomplete evidence, stated assumptions, separately sourced records that agree with the job, other applications that also disagree.
- Timeline entries with `event_time`, `time_basis`, `ingested_at` and `order_uncertain`. The timeline is ordered by event time; a record that arrived through an outbox is placed where it happened, not where it was ingested.

Contradictions enter the case as findings in the `cross_application` family, so they appear in the review queue and the priority score with everything else. Notes (`insufficient_evidence`, `unresolved_business_rule_conflict`) are shown and not scored.

## 8. What it cannot do

- **Consistent falsification from the first entry.** If a false value is in the source document, or typed once and copied everywhere, nothing contradicts anything. The system reports "all N records trace to one source; an independent authoritative source is required". It does not raise an anomaly and does not claim it could. Tested by scenarios `common_source_falsification` and `consistent_falsification`.
- **Decide which side is right.** A contradiction shows two records differ.
- **Establish independence of people.** Two tools may be operated by the same person.
- **Link without a reference.** A record with no job number and no container number stays unlinked.
- **See inside the desktop tools.** Only exports are captured.
- **Authenticate documents.** A forged checklist hashes as well as a real one.
- **Use outside authorities.** No carrier, customs or weighbridge data is available to it.
